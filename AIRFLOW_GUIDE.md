# Airflow: демонстрация интерфейса для ML-инженера

Локальный стенд: Airflow 3.3.2, три DAG-а, синтетические результаты, никакого обучения на реальных данных. Задачи занимают 12–30 секунд, чтобы смена статусов была заметна. Все запуски ручные (`schedule=None`).

## Отдельный запуск только Airflow (не основной сценарий)

Для полной связки использовать Docker Compose из README.md. Вариант ниже предназначен только для DAG-ов 01–03; DAG 04 требует общего стенда. Не запускать оба варианта одновременно: порт 8080 общий.

В PowerShell:

```powershell
cd D:\projects\airflow_ui_demo
.\start.ps1
```

Дождаться запуска компонентов и открыть http://localhost:8080. Логин: `admin`. Пароль создаётся при первом запуске и хранится локально:

```powershell
Get-Content D:\projects\airflow_ui_demo\.airflow\simple_auth_manager_passwords.json.generated
```

Оставить терминал открытым. Остановка — Ctrl+C в терминале запуска. История сохраняется в `.airflow`, повторный запуск её не удаляет. Если стенд уже запущен, второй экземпляр запускать не нужно.

На новой машине нужны WSL2 и Python с модулем venv. Перед первым запуском выполнить из PowerShell:

```powershell
wsl.exe -e bash /mnt/d/projects/airflow_ui_demo/install.sh
```

Пути в командах предполагают размещение стенда в `D:\projects\airflow_ui_demo`. Окружение `.venv` предназначено для Linux/WSL, не для Windows Python. При переносе переносить исходники, затем создавать окружение заново. Первый запуск и установка могут занимать несколько минут.

## Сценарий показа на 15–20 минут

### 1. Что именно оркестрирует Airflow — 2 минуты

«Есть шаги ML-процесса: загрузить данные, проверить, построить признаки, обучить модели, сравнить и сохранить результат. Airflow управляет их порядком и исполнением, хранит состояния и позволяет разбираться с ошибками».

- **DAG** — описание задач и зависимостей без циклов.
- **Task** — один шаг в описании.
- **DAG Run** — конкретный запуск всего графа.
- **Task Instance** — задача в конкретном запуске, с собственными статусом, логами и попытками.

В терминах Airflow нет отдельной обязательной сущности «стадия обучения»: это выбранные нами задачи и связи между ними.

### 2. Успешный запуск — 5 минут

1. В списке DAG-ов найти тег `ml-ui-demo`, открыть `demo_01_ml_pipeline`. При необходимости снять паузу.
2. Показать граф зависимостей (Graph). Проговорить маршрут:

```text
load_data → validate_data → build_features ┬→ train_linear   ─┐
                                          └→ train_boosting ─┴→ compare_models → save_result
```

3. Нажать Trigger / запуск, открыть созданный DAG Run и его граф.
4. Наблюдать, как задачи становятся `running` и `success`. Две задачи обучения могут работать одновременно; сравнение ждёт обеих.
5. Открыть выполняющуюся задачу → Logs. Найти сообщения `step 1/3`, `step 2/3`, `step 3/3`. При необходимости обновить отображение.
6. После завершения открыть результат/XCom у `compare_models`: небольшой словарь с моделью и условным AUC. Это демонстрационные числа.
7. Запустить DAG ещё раз. В истории появится отдельный запуск, хотя описание графа то же самое. Открыть Grid/историю запусков, сравнить статусы и длительности.

Полезный вопрос аудитории: «Если линейная модель уже готова, а бустинг ещё работает, может ли начаться сравнение?» Здесь ответ — нет, у задачи два обязательных предшественника.

### 3. Автоматическое восстановление — 3 минуты

1. Открыть `demo_02_auto_retry`, снять паузу и запустить.
2. У `fetch_data` первая попытка намеренно падает. Показать `up_for_retry` и текст ошибки в Logs.
3. Подождать: настроен один retry с задержкой 25 секунд. Планировщик может добавить небольшую задержку сверх неё.
4. Вторая попытка завершается успешно, затем запускается `train_model`.
5. Сравнить логи попыток. Объяснить: один DAG Run, одна Task Instance, несколько попыток исполнения.

### 4. Падение и ручной перезапуск — 4 минуты

1. Запустить `demo_03_manual_recovery` и дождаться завершения с ошибкой.
2. Показать `quality_gate = failed`, а у следующих задач — `upstream_failed`: сами они ещё не исполнялись.
3. Открыть Logs у `quality_gate`, найти `DEMO: quality check failed`.
4. Выбрать `quality_gate` → Clear. В диалоге включить downstream-задачи, ограничиться текущим запуском; проверить перечень перед подтверждением. `prepare_data` повторять не нужно.
5. Подтвердить и наблюдать успешное завершение того же DAG Run. Если интерфейс отдельно предлагает вернуть запуск в активное состояние, включить эту опцию.
6. Объяснить разницу: Trigger создаёт новый запуск; Clear сбрасывает состояния выбранных задач, позволяя планировщику выполнить их снова. Mark success только меняет статус и не выполняет код.

В этом стенде quality gate специально проходит со второй попытки. Это имитация исправленной внешней причины. В реальной работе сначала устраняют причину ошибки: нажатие Clear само по себе не исправляет данные или код.

### 5. Что происходит за интерфейсом — 2 минуты

Парсер читает файлы DAG-ов. Планировщик определяет готовые задачи с учётом зависимостей. Executor организует их выполнение; в стенде это локальные процессы. Состояния хранятся в базе метаданных, интерфейс показывает их и позволяет инициировать действия. Поэтому закрытие вкладки браузера не останавливает запущенный DAG.

В обычной эксплуатации DAG-и также запускают по расписанию или событиям. Здесь ручной запуск выбран специально для показа. Дата логического запуска и интервал данных — отдельные понятия; они не всегда совпадают со временем нажатия кнопки.

## Памятка по статусам

| Статус | Как объяснить |
|---|---|
| none | Задача ещё не назначена к исполнению, например ждёт зависимости |
| scheduled | Планировщик определил, что задачу можно запускать |
| queued | Задача передана исполнителю и ждёт выполнения |
| running | Код задачи исполняется |
| success | Выполнение успешно завершено |
| up_for_retry | Попытка неудачна, предусмотрен повтор |
| failed | Задача завершилась ошибкой |
| upstream_failed | Задача заблокирована ошибкой предшественника |

`scheduled` и `queued` могут проскочить быстрее обновления интерфейса. Не обещать аудитории, что каждый промежуточный статус удастся поймать. Есть и другие состояния, например `skipped` и `deferred`; эти три сценария их не демонстрируют.

## Перед записью

- Запустить стенд заранее, убедиться, что видны все три DAG-а и нет ошибок импорта.
- Открыть граф первого DAG-а и увеличить масштаб браузера под запись.
- Оставить примерно 2 минуты на успешный прогон; загрузка компьютера влияет на длительность.
- Для повторения сценария ошибки нажать Trigger, создав новый запуск. У нового запуска снова будет первая, намеренно неуспешная попытка.
- Названия/расположение элементов интерфейса могут отличаться от Airflow 2.x. Этот материал рассчитан на 3.3.2.
