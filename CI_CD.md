# CI/CD для локального ML-стенда

Workflow `.github/workflows/pipeline.yaml` запускается при push в `main`, pull request в `main` и вручную через Actions → Run workflow.

## Что видно в Actions

**Build and verify complete stack** работает на GitHub-hosted Linux runner:

1. Собирает образы Airflow, ML-сервиса, прокси и карты из текущего коммита для изолированных интеграционных проверок. В GHCR публикуется образ ML-сервиса и, при изменении DAG или связанного кода, образ Airflow.
2. Проверяет Compose и зависимости.
3. Поднимает отдельный стенд `ml-ci` с пустыми volumes.
4. Выполняет четыре учебных/обучающих DAG-а и отдельный недельный DAG пакетного скоринга; проверяет retry, Clear, настоящее предсказание, 1200 сохранённых batch-оценок, S3-артефакты, индексацию Qdrant и кэш Redis. Затем отдельно обучает модель без Airflow, регистрирует её в MLflow, временно назначает `production`, проверяет прогноз и откатывает alias.
5. Для `main` публикует проверенный образ ML-сервиса и при необходимости образ Airflow в GHCR. В CD передаются их неизменяемые digest.
6. Удаляет только временный CI-стенд и его данные.

**Deploy verified image to local demo** и **Release DAGs to Airflow** работают на Windows runner с меткой `ml-demo` на этом компьютере. Pull request эти этапы не запускает. Релиз DAG выполняется отдельно и только при изменении `dags/`, связанного кода или конфигурации Airflow.

CD загружает образ сервиса по digest и сверяет SHA. Одна из копий (`inference-blue` или `inference-green`) продолжает обслуживать запросы через постоянный адрес `inference:8000`; вторая обновляется. Перед переключением скрипт проверяет SHA, загрузку модели из MLflow/S3 и реальный прогноз на новой копии. После переключения проверяются запросы через прокси; при ошибке он возвращается к прежней копии. Airflow, MLflow, PostgreSQL, S3, Qdrant и Redis остаются работающими. Отдельный шаг CD загружает образ Airflow, меняет только его контейнер, проверяет обнаружение DAG-ов и ошибки импорта; при неудаче возвращает прежний образ Airflow. Во время этого шага UI Airflow может кратко перезапуститься, но ML-сервис продолжает отвечать.

ML-сервис и Airflow имеют отдельные образы и шаги CD. Изменение кода сервиса обновляет только его резервную копию и маршрутизацию; изменение DAG или связанного кода дополнительно выпускает образ Airflow. MLflow и другие инфраструктурные сервисы этими шагами не обновляются. CI проверяет новый код в одноразовом окружении до любого рабочего релиза.

Данные остаются в volumes проекта **ml-airflow-demo**. Код релиза находится внутри образа, без подключения рабочей папки. Обучение в рабочем стенде автоматически не запускается: CI обучает только в своём временном окружении, а в рабочем Airflow DAG по-прежнему запускается отдельно. Сервис `traffic` после развёртывания постоянно отправляет синтетические запросы в inference; CI/CD проверяет, что счётчик успешных прогнозов продолжает расти. Для паузы используйте `docker compose stop traffic`, для возобновления — `docker compose start traffic` из каталога репозитория.

## Что нужно для запуска

- Приватный GitHub-репозиторий с этим кодом и включёнными Actions.
- Зарегистрированный Windows x64 runner с дополнительной меткой `ml-demo`.
- Работающий Docker Desktop под пользователем runner.
- Уже обученная модель в рабочем стенде: CD проверяет её предсказание.

GHCR использует короткоживущий `GITHUB_TOKEN` задания. Пользовательские токены в репозиторий не добавляются. Для начального создания репозитория и регистрации runner нужен вход владельца через GitHub CLI с доступом `repo` и `workflow`.

## Где работает runner

Runner: `D:\projects\_tools\actions-runner-ml-demo`. Его рабочая папка и регистрационные файлы расположены вне репозитория. Запуск после перезагрузки Windows:

```powershell
cd D:\ml-platform-demo
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-runner.ps1
```

Это фоновый процесс текущего пользователя. Компьютер, Docker Desktop и runner должны работать для этапа CD. CI может завершиться на GitHub, пока компьютер выключен; CD тогда останется в очереди.

## Как показать обновление

1. Создать ветку, изменить текст на странице `service/index.html`, открыть pull request.
2. В Actions показать CI: сборка → запуск полного стенда → проверки.
3. После успешного CI объединить изменения в `main`.
4. Показать прошедшие CI и CD для нового commit.
5. Обновить http://localhost:8000 и открыть http://localhost:8000/version: SHA соответствует опубликованному коммиту. Сравнить ID контейнеров Airflow/MLflow до и после CD — они не меняются.
6. В `/model` остаются сведения о выбранной через MLflow модели. У внешней модели Git commit может отсутствовать; доставка кода сервиса не означает переобучение или смену alias.

Конфигурации релизов находятся в `D:\projects\_deploy\ml-airflow-demo\releases\<SHA>` (при повторной выкатке того же SHA добавляется дата и время), текущий релиз записан в `current.json`. Новые релизы также сохраняют `release.json` с точным образом и SHA. Исходная папка проекта остаётся рабочим Git-checkout; её локальные правки после CD не меняют работающий сервис.

Для ручного отката уже успешной выкатки найдите полный SHA прежнего коммита. В GitHub Actions откройте **Roll back ML service → Run workflow**, выберите ветку `main` и вставьте SHA в поле `revision`. Workflow авторизуется в GHCR временным `GITHUB_TOKEN`, затем запускает тот же скрипт деплоя с проверками.

Локально можно сначала посмотреть план, а затем запустить откат (Docker должен быть авторизован в приватном GHCR с правом `read:packages`):

```powershell
cd D:\ml-platform-demo
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\rollback.ps1 -Revision PASTE_FULL_SHA -Preview
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\rollback.ps1 -Revision PASTE_FULL_SHA
```

Скрипт использует точный digest из `release.json`, если прежний релиз его сохранил; для более старых релизов загружает образ из GHCR по тегу коммита. Он проверяет SHA внутри образа, прогревает свободную копию и переключает прокси после smoke checks. Airflow, MLflow и хранилища не переключаются. Не удаляйте нужные версии образа из GHCR: локальный кеш Docker может быть очищен.

Обычный `docker compose up` из рабочей папки возвращает режим разработки с bind mounts. Для управляемого релиза используйте workflow или `scripts/deploy_bluegreen.ps1`; локальный `git pull` сам по себе не является релизом. Подробный сценарий показа есть в [GUIDE_DEMO.md](GUIDE_DEMO.md).
