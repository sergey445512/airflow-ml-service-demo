# CI/CD для локального ML-стенда

Workflow `.github/workflows/pipeline.yaml` запускается при push в `main`, pull request в `main` и вручную через Actions → Run workflow.

## Что видно в Actions

**Build and verify complete stack** работает на GitHub-hosted Linux runner:

1. Собирает образ с кодом и Git SHA.
2. Проверяет Compose и зависимости.
3. Поднимает отдельный стенд `ml-ci` с пустыми volumes.
4. Выполняет четыре DAG-а, проверяет retry, Clear, настоящее предсказание и S3-артефакты.
5. Для `main` публикует проверенный образ в GHCR. В CD передаётся неизменяемый digest образа.
6. Удаляет только временный CI-стенд и его данные.

**Deploy verified image to local demo** работает на Windows runner с меткой `ml-demo` на этом компьютере. Pull request этот этап не запускает.

CD загружает образ, сверяет SHA, проверяет отсутствие активных DAG-ов и сохраняет конфигурацию прежнего развёртывания. Затем пересоздаёт контейнеры и делает настоящее предсказание. Если обновление или проверка не прошли, скрипт возвращает прежние контейнеры. Откат не отменяет изменения данных или миграции БД; в этом workflow миграций схемы приложения нет.

Данные остаются в volumes проекта **ml-airflow-demo**. Код релиза находится внутри образа, без подключения рабочей папки. Обучение в рабочем стенде автоматически не запускается: CI обучает только в своём временном окружении, а в рабочем Airflow DAG по-прежнему запускается отдельно.

## Что нужно для запуска

- Приватный GitHub-репозиторий с этим кодом и включёнными Actions.
- Зарегистрированный Windows x64 runner с дополнительной меткой `ml-demo`.
- Работающий Docker Desktop под пользователем runner.
- Уже обученная модель в рабочем стенде: CD проверяет её предсказание.

GHCR использует короткоживущий `GITHUB_TOKEN` задания. Пользовательские токены в репозиторий не добавляются. Для начального создания репозитория и регистрации runner нужен вход владельца через GitHub CLI с доступом `repo` и `workflow`.

## Где работает runner

Runner: `D:\projects\_tools\actions-runner-ml-demo`. Его рабочая папка и регистрационные файлы расположены вне репозитория. Запуск после перезагрузки Windows:

```powershell
cd D:\projects\airflow_ui_demo
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-runner.ps1
```

Это фоновый процесс текущего пользователя. Компьютер, Docker Desktop и runner должны работать для этапа CD. CI может завершиться на GitHub, пока компьютер выключен; CD тогда останется в очереди.

## Как показать обновление

1. Создать ветку, изменить текст на странице `service/index.html`, открыть pull request.
2. В Actions показать CI: сборка → запуск полного стенда → проверки.
3. После успешного CI объединить изменения в `main`.
4. Показать прошедшие CI и CD для нового commit.
5. Обновить http://localhost:8000 и открыть http://localhost:8000/version: SHA соответствует опубликованному коммиту.
6. В `/model` остаётся commit обучения текущей модели. Это другая версия: доставка кода не означает переобучение.

Конфигурации релизов находятся в `D:\projects\_deploy\ml-airflow-demo\releases\<SHA>`, текущий релиз записан в `current.json`. Исходная папка проекта остаётся рабочим Git-checkout; её локальные правки после CD не меняют работающий сервис.

Обычный `docker compose up` из рабочей папки возвращает режим разработки с bind mounts. Для управляемого релиза использовать workflow или `scripts/deploy.ps1`, а не смешивать эти способы запуска во время показа.
