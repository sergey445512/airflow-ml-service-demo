# Сценарий показа: от модели до релиза

Этот сценарий рассчитан на локальный стенд с Docker Desktop и подключённым GitHub runner. Команды выполняются из `D:\ml-platform-demo` в PowerShell. Исходные данные синтетические. Адреса: [карта](http://localhost:8090), [Airflow](http://localhost:8080), [MLflow](http://localhost:5000), [ML-сервис](http://localhost:8000), [Grafana](http://localhost:3000), [Adminer](http://localhost:8081).

## 1. Поднять стенд и проверить исходную модель

```powershell
cd D:\ml-platform-demo
docker compose up -d --build --wait
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-runner.ps1
docker compose exec airflow cat /opt/airflow/simple_auth_manager_passwords.json.generated
```

Последняя команда показывает пароль пользователя `admin` для Airflow. Откройте карту и убедитесь, что сервисы отвечают. Если этот стенд раньше уже запускался, модель и история сохранились в Docker volumes. Откройте `http://localhost:5000/#/models/churn-prediction`: у одной версии должен быть alias `production`. Точную обслуживаемую версию показывает `http://localhost:8000/model`; `http://localhost:8000/version` показывает commit кода. Если Registry пуст, запустите `demo_04_train_and_publish` в Airflow, дождитесь Success и вернитесь к этим страницам. Первое обучение назначает `production` автоматически.

## 2. Показать обучение и сохранение модели

В Airflow вручную запустите `demo_04_train_and_publish`. На карте откройте текущий запуск и следите за стадиями: подготовка клиентов в PostgreSQL, индексация в Qdrant, обучение и запись запуска в MLflow, сохранение артефакта в S3, регистрация версии и проверка онлайн-сервиса. Ожидаемый итог DAG — Success и новая версия `churn-prediction` в MLflow. Если alias уже существовал, новая версия остаётся кандидатом: `/model` продолжает показывать прежнюю production-версию. Это позволяет сравнить кандидата до продвижения.

В MLflow откройте **Models → churn-prediction**, сравните версии и назначьте кандидату alias `production`. Затем обновите `http://localhost:8000/model` и сделайте прогноз через `http://localhost:8000/docs` → `POST /churn/predict`. Ожидаемый результат: номер `model_version` и `mlflow_run_id` в ответе соответствуют выбранной версии. Сервис сам загружает артефакт из S3 через MLflow при первом запросе после смены alias.

## 3. Показать недельный пакетный расчёт

В Airflow вручную запустите `demo_05_weekly_batch_scoring` (по расписанию он идёт каждый понедельник в 03:00 UTC). На карте выберите этот запуск. Последовательность: зафиксировать production-версию → проверить клиентов → рассчитать и записать прогнозы → проверить результат. Ожидаемый итог — Success и 1200 строк за дату запуска в `app.churn_batch_scores`; версию модели и Airflow run ID видно в таблице через Adminer. Этот DAG использует ту же production-модель, но не отправляет 1200 отдельных HTTP-запросов в онлайн-сервис.

## 4. Показать Git → CI → CD

Для показа изменения кода создайте ветку и поменяйте `title` у `FastAPI(...)` в `service/app.py`, например добавьте «— релиз 2». Откройте pull request к `main`. На PR запускается CI: сборка образов, временный стек, DAG-и, прогноз, Registry, S3, мониторинг и хранилища. Рабочий стенд от PR не меняется. После merge в `main` CI публикует проверенный образ в GHCR, а локальный runner получает задание CD. Пока образ собирается, открывайте `/version` и карту: сервис отвечает через старую копию. CD запускает новую неактивную копию, проверяет загрузку модели и реальный прогноз, переключает прокси и сохраняет старую копию для отката. После Success `/version` показывает новый commit, а `http://localhost:8000/docs` — новое название; адрес сервиса не меняется.

Чтобы отдельно показать доставку DAG, в новом PR измените `description` у `demo_05_weekly_batch_scoring` в `dags/churn_batch_scoring.py` и смержите его после успешного CI. Появится шаг **Release DAGs to Airflow**, а шаг релиза ML-сервиса будет пропущен. Airflow проверит список DAG-ов и ошибки импорта. Новое описание появится в UI без ручного копирования файла на сервер. MLflow, S3 и онлайн-сервис остаются запущенными. UI Airflow может кратко перезапуститься.

Для отката к опубликованному commit откройте GitHub Actions → **Roll back ML service** и укажите полный SHA прежнего релиза. Скрипт снова готовит свободную копию и переключает прокси после проверки. Тот же запуск доступен локально через `scripts/rollback.ps1 -Revision <SHA> -Preview`, затем без `-Preview`.

## Локальная разработка и автоматический релиз — разные режимы

`git pull` в `D:\ml-platform-demo` обновляет только файлы на этом компьютере. При запуске обычным `docker compose up` код подключён как bind mount: Airflow перечитает DAG-файлы, а код сервиса потребует пересборки копий. Это удобно для разработки. Автоматический релиз происходит только после push/merge в `main`, успешного CI и выполнения CD на работающем локальном runner. Он использует код **в опубликованных образах**, а не файлы после локального `git pull`. Во время показа одного CD-релиза не запускайте поверх него обычный `docker compose up --build`.
